## 五、截图中告警和错误日志的根因

### 1. 先区分三个概念

- **最终请求错误日志**：客户端实际收到 4xx/5xx。
- **上游尝试错误日志**：某次上游返回 502，但切换其他账号后客户端可能收到 200。
- **告警事件**：一批错误可以同时触发“错误率高”“错误率极高”“成功率低”，并不代表三批独立故障。

### 3. 为什么少量空请求会显示 100% 错误率

当前监控口径：

```text
请求数 = usage_logs 中成功生成数 + 非业务限制的最终错误数
错误率 = 非业务限制的最终错误数 / 请求数
```

实现位于 `backend/internal/repository/ops_repo_dashboard.go:129`、`:930`。四条客户端参数错误被标记为 `client_request/client`，但 `is_business_limited=false`，因此仍计入服务错误率。对应窗口又没有成功模型生成记录，就会得到 1/1 或 3/3，即错误率 100%、成功率 0%。

`/health`、`/models`、`/usage` 的成功不会变成模型生成用量记录，不能抵消这些 400。原先我做了很多只读检查，也不意味着这些比例的分母会增加。

规则 8 是 1 分钟窗口错误率超过 20%，规则 1、2 是 5 分钟窗口的错误率超过 5%、成功率低于 95%，因此同一批请求可以出现三条 P0/P1 事件。当前没有最小样本数门槛，单个失败样本就能触发比例判断。

### 4. 为什么“告警中”可以挂很久

`ops_alert_evaluator_service.go:602` 起在窗口内没有请求时返回“无可计算指标”；`:230` 随即跳过本轮，既不新触发，也不恢复已有事件。所以没有新流量时，旧事件会一直显示“告警中”，其持续时间不能等同于服务器持续故障时间。

旧的 23:17/23:52 事件在本轮 09:12:18 有真实成功样本后由正常评估器恢复。本轮发现的真实续接失败又触发过新告警；最终取证时活动告警数为 0。没有手工恢复告警、删除记录或调高阈值。活动告警为 0 也不代表前述业务语义问题已经修复。

代码审查还发现一个需要回归的边界：连续次数不足时可能走到已有事件恢复分支，重启后计数重置会影响告警状态。建议把“达到持续次数才触发新事件”与“健康时才恢复已有事件”分开处理。本报告不把所有历史恢复都归因于这个边界。

### 5. 本轮额外发现的上游错误

- 尊享组有两次上游账号 12 返回 502，系统成功切换至其他账号，最终客户端均为 200。错误尝试保留在日志中，不能误判为两次最终调用失败。
- Messages 本轮 4 次最终 HTTP 400 是真实的会话续接兼容失败，和昨天空请求的 `model is required` 不同。
- 另外两次 HTTP 200 业务结果失败不会直接体现为 HTTP 错误率，这也是本次增加语义断言的原因。

## 六、建议处理顺序与验收边界

1. **正式切换前处理 Messages 会话续接。**至少要通过首轮、同会话重发、流式、tool_use→tool_result 多轮测试；不能只验证开关或普通问答。
2. **调整服务 SLA 与客户端参数错误的分类。**保留客户端错误供排查，服务可靠性指标应单独看网关/供应商故障；不要靠忽略 User-Agent 就把所有测试错误藏起来。
3. **增加可配置最小请求样本和无流量状态。**样本不足显示无数据/未知，避免一条失败长期呈现为全站 100% 故障。已有事件的冷启动、持续计数与恢复逻辑也需回归。
4. **把恢复成功的上游尝试与最终失败分开展示。**账号 12 的 502 需要关注，但也应显示后续切换成功。
5. **核对性价比组的长输入计量。**短提示上报约 2.24 万输入 Token 的原因尚未最终确认，不应未经核对就修改用户账单或倍率。

## 400 根因确认、修复及实机验证

### 1. 已确认的根因与责任边界

这次不是迁移密码、余额或 Key 数据的问题。sub2api 在 Messages→Responses 转换时，默认对 APIKey 账号自动启用有状态续接：缓存第一轮 response_id，第二轮附加 `previous_response_id`，并裁剪已发送的历史。当前实际使用的 Flux 账号/HTTP Responses 接口不兼容这种续接请求，直接返回通用 400；旧代码仅在错误消息明确提到 previous_response_id 不可用时才回退，因此没有捕获这次通用错误。

绕过 sub2api、直接使用新站上游账号 1 的同一 URL 与凭据，做了以下对照。全部使用合成短提示，低推理强度，不发送真实用户聊天内容；凭据只在服务器进程内读取，不进入公开报告。

| 直连上游场景 | 结果 |
| --- | --- |
| 首轮，store=false，无 previous_response_id | 200，READY |
| 第二轮，store=false，带首轮 previous_response_id | 400，Upstream request failed |
| 完整历史，不带 previous_response_id | 200，正确返回第一轮随机代码 |
| 首轮，store=true，无 previous_response_id | 200，READY |
| 第二轮，store=true，带首轮 previous_response_id | 400，Upstream request failed |

后两项是严格的单参数对照，避免把“同时改变历史与续接 ID”误当成只由该参数触发。这确认了故障触发条件是当前上游的 previous_response_id 续接方式，单独将 store 改为 true 不能解决。不能据此推断所有 Flux 产品或所有供应商都不支持该参数；供应商内部拒绝的更深层原因没有从通用错误中披露，但修复所需的兼容性边界已通过对照确认。
